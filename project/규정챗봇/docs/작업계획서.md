# 규정챗봇 재설계 작업계획서

## 1. 작업 목적

기존 `규정챗봇` 프로젝트를 RAG/벡터DB 중심 구조가 아니라, Markdown 문서의 조항 구조를 명시적으로 인덱싱하고 검증 가능한 근거만 사용해 답변하는 사내 규정 근거형 AI 캐릭터 챗봇으로 재설계한다.

1차 목표는 실제 사내 메신저 연동이 아니라 Electron 기반 가상 메신저 데모와 Django 백엔드 설계다.

## 2. 핵심 요구사항

- HWP/HWPX/PDF 규정, 지침, 매뉴얼 문서를 로컬 `kordoc`으로 Markdown 변환
- Markdown 파일명과 본문 구조에서 규정명, 개정일, 조, 항, 별표, 부칙 추출
- 질문이 들어오면 백엔드가 먼저 후보 근거를 확정
- LLM은 확정된 근거 안에서만 답변 생성
- 모든 답변은 최소 `규정명 + 조 + 항` 근거 포함
- 근거가 부족하면 추정하지 않고 `확인 가능한 근거 없음` 반환
- 질문 의도가 불명확하면 답변이나 담당자 안내보다 재질문 우선
- 규정 답변 이후 운영 문의가 필요한 경우에만 담당자 연락처 안내
- AI 캐릭터는 조직별 담당 문서 범위 안에서만 답변
- AI 캐릭터별 최대 10개 규정 및 매뉴얼 업로드 지원
- 업무 범위 밖 질문은 적합한 다른 AI 캐릭터를 먼저 추천
- Django 관리자 화면에서 조직도, AI 캐릭터, LLM API 키를 관리
- Electron 데모는 Django 로그인 후 사용
- API 키, 인증값, 원본문서, 로그, DB 파일은 GitHub 배포 대상에서 제외

## 3. 설계 원칙

### 3.1 근거 확정 후 답변

LLM이 문서 검색과 근거 판단을 직접 수행하지 않는다. 검색, 후보 근거 선정, 근거 검증은 백엔드가 담당한다.

### 3.2 LLM 교체 가능 구조

Gemini를 1차 기본값으로 두되, OpenAI와 Claude를 같은 인터페이스로 교체할 수 있게 한다.

공통 출력 구조는 다음을 기준으로 한다.

```json
{
  "answer": "답변 본문",
  "citations": [
    {
      "document_title": "규정명",
      "article": "제1조",
      "paragraph": "제1항",
      "appendix": null
    }
  ],
  "confidence": "high",
  "missing_evidence_reason": null
}
```

### 3.3 보수적 실패

다음 경우에는 답변을 차단한다.

- 근거 조항이 실제 인덱스에 없음
- 답변에 조항 근거가 없음
- 사용자 질문이 캐릭터의 담당 문서 범위를 벗어남
- 문서 또는 질문에 프롬프트 인젝션 지시가 포함됨
- LLM 출력 JSON 구조가 검증되지 않음
- LLM API 키가 설정되지 않았거나 연결 테스트에 실패함

### 3.4 담당자 안내는 보조 정책

담당자 연락처는 답변 실패를 덮기 위한 수단이 아니다. 규정과 매뉴얼 근거를 충분히 검토한 뒤, 실제 적용·예외 승인·시스템 입력·제출처 확인처럼 사람의 운영 판단이 필요한 경우에만 답변 하단에 안내한다.

질문 의도가 불명확하면 다음 순서로 처리한다.

1. 질문 의도 분류
2. 후보 문서와 조항 확인
3. 부족한 조건을 재질문
4. 근거가 확인된 뒤 답변
5. 필요 시 담당자 안내

### 3.5 기능 확정과 변경 이력 관리

작은 기능은 확정 가능한 단위로 나누고, 확정된 기능의 동작을 프롬프트 변경으로 흔들지 않는다. 개선이 필요하면 정책 모듈, 함수, 어댑터를 추가해 확장한다.

기능 정의와 변경 이력은 `docs/기능정의_변경보고서.md`에 누적 관리한다.

## 4. 단계별 작업계획

### Phase 1. 문서 기반 정리

- README를 새 설계 기준으로 재작성
- `.gitignore`에 규정챗봇 원본문서, 파싱 산출물, DB, 로그, Electron 빌드 산출물 제외 규칙 추가
- `.env.example` 초안 작성
- 샘플 문서 목록과 1차 데모 대상 캐릭터 정의
- 기능 정의 및 변경 보고서 생성
- 첨부 조직도는 가명 데모 데이터로만 반영

완료 기준:

- README에서 RAG/ChromaDB/Streamlit 중심 설명 제거
- 보안 제외 규칙 명시
- `이평가` 캐릭터와 `성과평가지침` 예시 시나리오 명시
- 담당자 안내, 재질문, 업무 범위 라우팅 정책 명시
- 1차 데모가 mock 없이 API 기반임을 명시

### Phase 2. 문서 파싱 파이프라인

- `kordoc` 최신 CLI 기준 문서 변환 명령 정리
- `data/raw/`의 HWP/HWPX/PDF를 Markdown으로 변환하는 스크립트 작성
- 파싱 결과 저장 위치를 `docs/parsed/`로 고정
- PDF 품질 신호와 OCR 필요 여부를 기록할 수 있는 구조 검토
- 관리자 업로드 허용 확장자를 `.hwp`, `.hwpx`, `.pdf`로 제한
- 캐릭터별 연결 문서 수를 최대 10개로 제한

완료 기준:

- 샘플 `성과평가지침` 문서를 Markdown으로 변환
- 변환 실패 시 원인과 파일명을 안전하게 기록
- 로그에 내부 경로, 개인정보, API 키가 노출되지 않음
- 지원하지 않는 확장자는 사용자 안내 메시지와 함께 거부
- 새 문서 업로드 후 조항 인덱스와 캐릭터 업무 카탈로그 갱신

### Phase 3. 조항 인덱스

- Markdown 파일명에서 규정명과 개정일 추출
- 본문에서 `제N조`, `제N항`, `별표`, `부칙` 패턴 추출
- 조항 단위 인덱스 모델 정의
- 인덱스 생성 결과를 DB에 저장
- 동일 규정의 개정일이 다를 경우 최신본 우선 규칙 정의
- 이전 문서 버전은 비활성 상태로 보존

완료 기준:

- 규정명, 조, 항 기준 검색 가능
- 별표와 부칙은 보조 근거로 연결 가능
- 인덱스 없는 문서에 대해 답변하지 않음
- 감사 로그에서 답변에 사용된 문서 버전 추적 가능

### Phase 4. Django 백엔드

- Django 프로젝트 생성
- 조직, 부서, 사용자, AI 캐릭터, 문서, 조항 인덱스, 질의 로그, 감사 로그 모델 정의
- 담당자, 담당 업무 키워드, 캐릭터 업무 범위 카탈로그 모델 정의
- LLM 공급자와 암호화 SecretCredential 모델 정의
- REST API 또는 Django Ninja API로 질의 엔드포인트 구성
- Django Channels로 WebSocket 채팅 엔드포인트 구성
- 관리자 페이지에서 문서와 캐릭터 매핑 관리
- 관리자 페이지에서 캐릭터별 최대 10개 문서 업로드 및 최신화 관리
- 관리자 페이지에서 LLM API 키 입력, 암호화 저장, 연결 테스트 지원
- Django Auth 기반 로그인과 권한 그룹 구성
- `django-unfold` 관리자 테마 적용

완료 기준:

- 캐릭터별 접근 가능 문서 범위 적용
- 질문 요청마다 근거 후보 선정, LLM 호출, 출력 검증, 감사 로그 저장 수행
- 근거가 없으면 실패 응답 반환
- 질문 의도가 불명확하면 재질문 반환
- 업무 범위 밖 질문은 적합한 다른 캐릭터 추천 또는 답변 불가 안내
- 담당자 안내는 정책 조건을 만족할 때만 답변 하단에 표시
- API 키 원문은 저장 후 다시 표시되지 않음
- 조직도와 AI 캐릭터는 관리자 화면에서 추가, 수정, 삭제 가능

### Phase 5. LLM 어댑터

- `LLMProvider` 공통 인터페이스 정의
- Gemini Provider 1차 구현
- OpenAI Provider와 Claude Provider는 동일 인터페이스로 확장 가능하게 준비
- 구조화 JSON 출력 검증 로직 작성
- 프롬프트 인젝션 방어용 시스템 메시지와 데이터 분리 규칙 적용
- `provider_api` 실행 모드로 1차 데모 고정
- API 키는 관리자 화면에서 암호화 저장하고 Electron에 전달하지 않음
- `.env`에는 `SECRET_ENCRYPTION_KEY` 등 부팅에 필요한 최소 Secret만 저장

완료 기준:

- LLM에는 확정된 근거 조각만 전달
- LLM 출력이 스키마와 근거 검증을 통과해야만 사용자에게 표시
- 공급자 API 키는 암호화 Secret 저장소에서만 복호화해 사용
- API 키가 없으면 명확한 설정 오류 반환
- 공급자별 연결 테스트 가능

### Phase 6. Electron 데모

- 좌측 조직/AI 캐릭터 목록, 중앙 대화 화면, 우측 근거 패널 구성
- Django 로그인 기반 사용자 인증 적용
- 답변 하단에 담당자 안내 영역 구성
- 업무 범위 밖 질문 시 추천 캐릭터 안내 UI 구성
- Electron renderer는 Django API와만 통신
- `nodeIntegration: false`, `contextIsolation: true`, sandbox, CSP 적용
- 제한된 IPC만 preload에서 노출

완료 기준:

- `이평가` 캐릭터 선택 후 성과평가지침 관련 질문 가능
- 답변과 근거 패널이 함께 표시
- 필요한 경우 담당자 정보가 하단에 표시
- 의도 불명확 질문은 재질문 형태로 표시
- 로그인하지 않은 사용자는 데모 메신저 사용 불가
- Electron renderer에서 Node.js API 직접 접근 불가

## 5. 보안 체크리스트

- `.env`, `*.env` Git 제외
- `data/raw/` Git 제외
- `docs/parsed/` Git 제외
- `*.sqlite`, `*.sqlite3`, `db.sqlite3` Git 제외
- `*.log`, `logs/` Git 제외
- `desktop/**/dist/`, `desktop/**/out/`, `desktop/**/node_modules/` Git 제외
- `.env.example`에는 placeholder만 포함
- API 키와 인증 헤더는 로그에 남기지 않음
- 사용자 입력을 파일 경로, SQL, 외부 명령에 직접 삽입하지 않음
- 문서 내용 안의 지시는 명령이 아니라 데이터로만 취급
- Electron에는 LLM API 키를 저장하지 않음
- API 키 입력 화면은 HTTPS, CSRF, 권한, 재인증, 마스킹을 적용
- 담당자 연락처는 권한과 업무 범위 조건을 만족할 때만 표시

## 6. 테스트 계획

### 문서 테스트

- README에 새 설계 원칙이 모순 없이 반영되었는지 확인
- 기존 RAG/ChromaDB/Streamlit 전제가 제거되었는지 확인

### 파싱 테스트

- 샘플 HWP/HWPX/PDF 파일을 `kordoc`으로 Markdown 변환
- 변환 결과에서 규정명, 조, 항 추출 가능 여부 확인

### 답변 테스트

- 근거가 있는 질문은 답변과 근거를 함께 반환
- 근거가 없는 질문은 `확인 가능한 근거 없음` 반환
- 조항 번호 없는 LLM 답변은 차단
- 의도 불명확 질문은 재질문 반환
- 업무 범위 밖 질문은 다른 캐릭터 추천 또는 답변 불가 반환
- 담당자 안내 조건을 만족하지 않으면 연락처 미표시

### 보안 테스트

- `.env`, 원본문서, DB, 로그가 Git 추적 대상이 아닌지 확인
- 프롬프트 인젝션 문구가 포함된 질문에도 시스템 정책이 유지되는지 확인
- Electron renderer에서 Node.js API가 노출되지 않는지 확인
- 관리자 API 키 입력 화면에서 원문 키가 로그와 응답에 남지 않는지 확인
- 로그인하지 않은 사용자가 Electron 데모 API를 사용할 수 없는지 확인

## 7. 현재 결정사항

- 1차 시연: Electron 기반 가상 사내 메신저
- 백엔드: Django + Django Channels
- LLM 구조: Gemini/OpenAI/Claude 교체 가능 구조
- 1차 기본 LLM: Gemini 계열
- 1차 데모 실행 모드: provider API
- 관리자 테마: `django-unfold` 우선
- 답변 근거 최소 단위: `규정명 + 조 + 항`
- 캐릭터별 업로드 문서 제한: 최대 10개
- 허용 파일 형식: `.hwp`, `.hwpx`, `.pdf`
- 실제 조직도와 사내 메신저 연동 방식: 추후 반영
